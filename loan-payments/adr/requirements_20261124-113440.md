# Requirements: Loan Payments (personal loans)

## Goal

Give each personal-loan customer an API to look up their own loans: the payment summary of each
loan and the payments of each loan. The customer signs in through the SSO, and the API shows only
the loans of the `customer_id` in their JWT.

## Scope

**In scope:**

- A new DataSQRL project in `loan-payments/` that reads the finance data catalog
  (`data-catalog/`, a git submodule at the repository root) and does not change it.
- The table `LoanPayments`: one row per payment of a personal loan, with the customer id and the
  loan purpose from the loan record.
- The table `LoanPaymentSummary`: one row per personal loan, with payment counts and totals.
- An API with the three lookups in [API surface](#api-surface), authorized by the JWT claim
  `customer_id`.
- Tests that use the test data of the catalog.
- A `test` and a `prod` environment, with the same layout as the sibling project `lending/`
  (`lending360-shared-package.json`, `lending360-test-package.json`, `lending360-prod-package.json`).

**Out of scope:**

- Auto loans and auto-loan payments. The catalog table `Loan_Payment` holds both, and this project
  keeps only `loan_type = 'PERSONAL'`.
- Mortgages, credit cards and delinquency events.
- Payment submission or any other write to the source systems. The API has no mutations.
- Staff or admin access to the loans of other customers.
- Changes to the data catalog, its schemas or its test data.
- A web UI.

## Functional requirements

- **FR-1**: Read the personal loans from the catalog table `Personal_Loan` and the payments from
  the catalog table `Loan_Payment` (dataset `lending/cards_consumer_credit/consumer_loans`).
- **FR-2**: Keep the latest version of each personal loan (key `loan_id`) and of each payment
  (key `payment_id`), by `source_updated_at`. Both sources are CDC streams.
- **FR-3**: Keep only the payments of personal loans: `loan_type = 'PERSONAL'` and a `loan_id`
  that exists in `Personal_Loan`.
- **FR-4**: `LoanPayments` has one row per `payment_id`. Each row has the payment fields listed in
  [Transformations](#transformations-and-aggregations), plus `customer_id`
  (= `Personal_Loan.primary_borrower_customer_id`) and `loan_purpose` from the loan record.
- **FR-5**: `LoanPayments` keeps payments of every status (`APPLIED`, `PENDING`, `RETURNED`,
  `REVERSED`) so that a customer sees their returned payments.
- **FR-6**: `LoanPaymentSummary` has one row per personal loan, with `loan_id`, `customer_id`,
  `loan_purpose` and these values:
  - `applied_payment_count`: the number of payments with `payment_status = 'APPLIED'`.
  - `returned_payment_count`: the number of payments with `payment_status = 'RETURNED'`.
  - `total_paid_cents`: the sum of `payment_amount_cents`.
  - `principal_paid_cents`: the sum of `principal_cents`.
  - `interest_paid_cents`: the sum of `interest_cents`.
  - `late_fees_paid_cents`: the sum of `late_fee_cents`.
  - `last_payment_date`: the latest `applied_date`.
- **FR-7**: The totals and `last_payment_date` in FR-6 use only the payments with
  `payment_status = 'APPLIED'`. A `RETURNED`, `PENDING` or `REVERSED` payment adds nothing to them.
- **FR-8**: When a payment changes status (for example `APPLIED` to `RETURNED`), the summary of its
  loan uses only the latest status.
- **FR-9**: Query `LoanPaymentSummary` by `loan_id`.
- **FR-10**: Query the `LoanPayments` of a loan by `loan_id`.
- **FR-11**: Query all loans of a customer, each with its summary, by `customer_id`.
- **FR-12**: Every query returns only rows whose `customer_id` equals the JWT claim `customer_id`.
  A request for a loan of another customer returns no rows.
- **FR-13**: A request without a valid JWT, or with a JWT that has no `customer_id` claim, is
  rejected.

## Sources

Both sources are catalog tables that the project imports. The project manages no data itself.

### `Personal_Loan` (catalog)

- **Ownership**: external. The consumer lending system publishes it. The project only reads it.
- **Catalog files**: schema `data-catalog/lending/cards_consumer_credit/consumer_loans.sqrl`
  (`Personal_Loan_schema`), connectors `consumer_loans-test.sqrl` and `consumer_loans-prod.sqrl`.
- **Transport**: test: file `testdata/consumer_loans-personal_loan.jsonl`. prod: Kafka topic
  `consumer_loans.personal_loan` on `${LENDING_KAFKA_BROKERS}`.
- **Format**: JSON, ISO-8601 timestamps. No schema registry.
- **Sample payload** (test data):

  ```json
  {"loan_id":"PL-011","application_id":"LAPP-023","primary_borrower_customer_id":"CUST-066",
   "loan_number":"PL-2020-28229","loan_status":"PAID_OFF","loan_purpose":"MAJOR_PURCHASE",
   "original_amount_cents":1740000,"current_balance_cents":0,"interest_rate":0.1566,
   "rate_type":"FIXED","original_term_months":24,"remaining_term_months":0,
   "monthly_payment_cents":84913,"funding_date":"2020-09-11","first_payment_date":"2020-10-11",
   "maturity_date":"2022-09-11","next_payment_due_date":null,"paid_off_date":"2022-09-04",
   "origination_fee_cents":34800,"credit_score_at_origination":644,"dti_at_origination":24.62,
   "autopay_enrolled":true,"disbursement_account_id":"ACCT-140","payment_account_id":"ACCT-140",
   "origination_channel":"BRANCH","source_system":"CONSUMER_LENDING",
   "source_updated_at":"2022-09-04T12:40:57Z","ingested_at":"2022-09-04T12:44:22Z"}
  ```

  Nullable fields used by this project: `loan_purpose`. `loan_id` and
  `primary_borrower_customer_id` are `NOT NULL`.
- **Volume and rate**: test data: 170 loans, 142 customers. Production volume is an open question.
- **Delivery guarantee**: at-least-once (Kafka, `kafka-safe` connector). Replay from the earliest
  offset is possible.
- **Duplicates and ordering**: a CDC stream. Several versions of a `loan_id` can arrive. The latest
  `source_updated_at` wins.
- **Updates**: CDC updates to prior state (for example `ACTIVE` to `PAID_OFF`).

### `Loan_Payment` (catalog)

- **Ownership**: external, the same consumer lending system.
- **Catalog files**: schema `Loan_Payment_schema` in the same `consumer_loans.sqrl`, with the same
  connector files.
- **Transport**: test: file `testdata/consumer_loans-loan_payment.jsonl`. prod: Kafka topic
  `consumer_loans.loan_payment`.
- **Format**: JSON, ISO-8601 timestamps.
- **Sample payload** (test data, a returned payment):

  ```json
  {"payment_id":"LPMT-046","loan_id":"PL-115","loan_type":"PERSONAL","payment_amount_cents":57760,
   "principal_cents":37108,"interest_cents":20652,"late_fee_cents":0,"other_fees_cents":0,
   "payment_type":"REGULAR","payment_status":"RETURNED","due_date":"2025-10-08",
   "received_date":"2025-10-05","applied_date":"2025-10-05","payment_method":"ACH",
   "principal_balance_after_cents":1632892,"days_past_due_at_payment":0,
   "confirmation_number":"ACH-20251005-00046","return_reason_code":"R01",
   "source_system":"CONSUMER_LENDING","source_updated_at":"2025-10-05T14:36:25Z",
   "ingested_at":"2025-10-05T14:39:42Z"}
  ```

  Nullable fields: `principal_cents`, `interest_cents`, `late_fee_cents`, `other_fees_cents`,
  `received_date`, `applied_date`, `payment_method`, `principal_balance_after_cents`,
  `days_past_due_at_payment`, `confirmation_number`, `return_reason_code`.
- **Volume and rate**: test data: 1,942 payments. 1,010 are personal (1,001 `APPLIED`,
  9 `RETURNED`). The test data has no `PENDING` or `REVERSED` payment.
- **Delivery guarantee**: at-least-once.
- **Duplicates and ordering**: a CDC stream. Deduplicate on `payment_id`, the latest
  `source_updated_at` wins.
- **Updates**: CDC. A payment can change status after it arrives.

## Time semantics

- **Event-time field**: `ingested_at` (`TIMESTAMP_LTZ(3)`, UTC). The catalog connectors set the
  watermark on it: 10 seconds in test, 30 seconds in prod. The project uses these watermarks as
  they are.
- **Version order**: `source_updated_at` picks the latest version of a loan or a payment.
- **Lateness**: a payment that arrives late still counts. The summary is not windowed, so a late
  payment updates the summary of its loan.
- **Processing time**: not used.

## Entities and keys

| Entity | Key | Source | Relations |
|---|---|---|---|
| Personal loan | `loan_id` | catalog `Personal_Loan` | belongs to one customer (`primary_borrower_customer_id`) |
| Payment | `payment_id` | catalog `Loan_Payment` | belongs to one loan (`loan_id`) |
| Customer | `customer_id` | the JWT claim, and `Personal_Loan.primary_borrower_customer_id` | has zero or more personal loans |

The `customer_id` of a payment comes from its loan, not from the payment record.

## Transformations and aggregations

1. **Latest loans**: the latest version of each `Personal_Loan` by `source_updated_at`, key
   `loan_id`. All loan statuses stay (`ACTIVE`, `PAID_OFF`, `CHARGED_OFF`, `SETTLED`).
2. **Latest payments**: the latest version of each `Loan_Payment` by `source_updated_at`, key
   `payment_id`, filtered to `loan_type = 'PERSONAL'`.
3. **`LoanPayments`**: latest payments joined to latest loans on `loan_id` (inner join). Columns:
   `payment_id`, `loan_id`, `customer_id`, `loan_purpose`, `payment_amount_cents`,
   `principal_cents`, `interest_cents`, `late_fee_cents`, `other_fees_cents`, `payment_type`,
   `payment_status`, `due_date`, `received_date`, `applied_date`, `payment_method`,
   `principal_balance_after_cents`, `days_past_due_at_payment`, `confirmation_number`,
   `return_reason_code`. Default order: `due_date` descending, then `payment_id`.
4. **`LoanPaymentSummary`**: group `LoanPayments` by `loan_id`, with the values of FR-6 and the
   filter rule of FR-7. Window: none (unbounded, updated on each change). A loan without payments
   gets a row with counts and sums of 0 and a null `last_payment_date` (see Open Questions).

Amounts stay in cents (`BIGINT`), the same unit as the catalog.

## Results

### `LoanPayments` and `LoanPaymentSummary`

- **Kind**: API (served from the database of the project).
- **Consumers**: personal-loan customers, through the client app of the bank.
- **Authorization**: authorized. The JWT from the SSO carries the claim `customer_id`. Every query
  filters on `customer_id = <claim customer_id>`. No other claim gives access.

## API surface

- **Queries** (all filtered by the JWT claim `customer_id`, see FR-12):
  - `LoanPaymentSummary(loan_id)`: the summary of one loan. Returns 0 or 1 row.
  - `LoanPayments(loan_id)`: the payments of one loan, newest due date first, paged
    (`limit`, `offset`).
  - Loans of a customer: all personal loans of the signed-in customer, each with its summary.
    The `customer_id` comes from the JWT claim, so the caller cannot ask for another customer.
- **Mutations**: none.
- **Subscriptions**: none.
- **Protocols**: GraphQL, REST and MCP, the same as the sibling project `lending/`.
- **Access**: every query needs a valid JWT with the claim `customer_id`.

## Test data and acceptance criteria

- **Test data**: the catalog test data in
  `data-catalog/lending/cards_consumer_credit/testdata/`
  (`consumer_loans-personal_loan.jsonl`, `consumer_loans-loan_payment.jsonl`), read through the
  catalog test connectors. The project adds no source data of its own.
- **Edge cases in that data**:
  - Auto-loan payments (932 rows) that the filter must remove.
  - 9 `RETURNED` personal payments, on loans `PL-023`, `PL-061`, `PL-062`, `PL-068`, `PL-071`,
    `PL-079`, `PL-108`, `PL-115`, `PL-121`.
  - 26 applied personal payments with `late_fee_cents > 0`.
  - 35 personal loans without payments (for example `PL-011`, `PL-014`).
  - 23 customers with more than one personal loan (for example `CUST-060` with `PL-006`,
    `PL-007`, `PL-022`, `PL-033`).
  - Loans in every status (`ACTIVE` 114, `PAID_OFF` 51, `CHARGED_OFF` 4, `SETTLED` 1).
- **Acceptance criteria**:
  - *(FR-1, FR-3)* `LoanPayments` has 1,010 rows. No row has a `loan_id` that starts with `AL-`.
  - *(FR-2)* `LoanPayments` has one row per `payment_id`, and `LoanPaymentSummary` has one row
    per `loan_id`.
  - *(FR-4)* Each `LoanPayments` row has the `customer_id` and `loan_purpose` of its loan in
    `Personal_Loan`.
  - *(FR-5)* `LoanPayments(loan_id: "PL-115")` includes payment `LPMT-046` with
    `payment_status = "RETURNED"` and `return_reason_code = "R01"`.
  - *(FR-6, FR-7)* For `PL-115`, `returned_payment_count = 1`, and `total_paid_cents` equals the
    sum of `payment_amount_cents` of its `APPLIED` payments only (it excludes the 57,760 of
    `LPMT-046`). The planner computes the expected values from the test data.
  - *(FR-6)* For a loan with applied late fees, `late_fees_paid_cents` equals the sum of their
    `late_fee_cents`.
  - *(FR-6)* For `PL-011` (no payments), the summary row has counts and sums of 0 and a null
    `last_payment_date`.
  - *(FR-8)* Not testable with the catalog test data, because no payment changes status in it.
    The plan says how it covers this rule.
  - *(FR-9, FR-12)* With a JWT for `CUST-439` (the customer of `PL-115`), `LoanPaymentSummary(loan_id: "PL-115")`
    returns 1 row. With a JWT for `CUST-060`, the same query returns 0 rows.
  - *(FR-10, FR-12)* With a JWT for `CUST-060`, `LoanPayments(loan_id: "PL-115")` returns 0 rows.
  - *(FR-11)* With a JWT for `CUST-060`, the customer query returns the 4 loans `PL-006`, `PL-007`,
    `PL-022`, `PL-033`, each with its summary.
  - *(FR-13)* A request without a JWT gets an authorization error.
  - Snapshot tests store the API responses above under the test folder of the project.

## Non-functional requirements

- **Freshness**: a new or changed payment shows in `LoanPayments` and `LoanPaymentSummary` within
  1 minute of its arrival in Kafka (see Open Questions).
- **API latency SLA**: p99 < 200 ms for each query, at up to 50 requests/second (see Open Questions).
- **Workload**: unknown in production (see Open Questions). The test data has 170 loans and
  1,010 personal payments.
- **Budget**: none stated (see Open Questions).
- **Reliability**: no data loss. After a failure, the pipeline restarts from its last checkpoint
  and replays from Kafka.
- **Retention**: the API keeps all payments of all personal loans, with no expiry.
- **PII and sensitive fields**: `customer_id` is tagged `@pii`. The amounts are `@npi`. The API
  shows them only to the customer that owns the loan (FR-12). The API leaves out `loan_number`
  (`@npi @mask`), the account ids, the credit score and the DTI ratio.
- **Compliance**: GLBA, GDPR, CCPA, the same as the catalog dataset. No new storage outside the
  database of the project.
- **Availability**: no target stated. The default deployment of DataSQRL Cloud applies.

## Hard constraints

- Use the catalog tables `Personal_Loan` and `Loan_Payment` from `data-catalog/` through
  `script.include`, the same way as `lending/lending360-shared-package.json`. Do not copy or
  re-declare them. Reason: the user asked to use the finance data catalog.
- Use the catalog test data for the tests. Reason: the user asked for it.
- Use the table names `LoanPayments` and `LoanPaymentSummary`. Reason: the user named them.
- Authorize with the JWT claim `customer_id` from the SSO. Reason: the user stated it.

## Open Questions

- **Freshness**: how fast must a payment show in the API? Recommended default: *within 1 minute,
  with the streaming Flink pipeline of the sibling `lending/`*. Impact if wrong: high.
- **JWT validation**: which signing algorithm, issuer, audience and key does the SSO use?
  Recommended default: *HS256 with a fixed test secret in `test`, and the key from an environment
  variable (for example `${JWT_SECRET}`) in `prod`*. Impact if wrong: high.
- **Production workload**: how many loans and payments per day, and how many API requests per
  second? Recommended default: *up to 1 million personal loans, 50,000 payments per day, and
  50 requests/second peak*. Impact if wrong: medium.
- **Last payment date**: is it the latest `applied_date` of an applied payment, or the latest
  `received_date`? Recommended default: *the latest `applied_date` of an `APPLIED` payment*.
  Impact if wrong: low.
- **Total amount paid**: is it `payment_amount_cents` (the full payment, which includes fees)?
  Recommended default: *yes, the sum of `payment_amount_cents` of applied payments*. Impact if
  wrong: low.
- **Loans without payments**: does `LoanPaymentSummary` show a row for a loan with no payments?
  Recommended default: *yes, with counts and sums of 0 and a null `last_payment_date`*. Impact if
  wrong: medium.
- **Loan status**: does the API show loans in every status, or only `ACTIVE` loans? Recommended
  default: *every status*. Impact if wrong: medium.
- **Loan details in the customer query**: does the customer query show loan fields other than the
  summary (for example `loan_status`, `current_balance_cents`)? Recommended default: *add
  `loan_status`, `original_amount_cents`, `current_balance_cents`, `monthly_payment_cents` and
  `next_payment_due_date`*. Impact if wrong: low.
- **API protocols**: GraphQL, REST and MCP, or GraphQL only? Recommended default: *all three, the
  same as `lending/`*. Impact if wrong: low.
- **Budget**: what may the pipeline cost per month? Recommended default: *the smallest DataSQRL
  Cloud deployment size*. Impact if wrong: low.
