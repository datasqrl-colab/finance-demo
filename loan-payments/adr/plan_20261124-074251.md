# Implementation Plan: Loan Payments — customer self-service payment view for personal loans

**Scenario**: pipeline
**Task**: new-project
**Date**: 2026-11-24T07:42:51Z
**Status**: DRAFT

A new streaming DataSQRL pipeline that reads personal loans and loan payments from the shared
consumer-lending data catalog, deduplicates their CDC streams, joins payments to personal loans,
and serves a per-payment and per-loan payment summary through a JWT-restricted GraphQL/REST/MCP
API. It reuses the shared `data-catalog` module and mirrors the sibling `lending` project's
architecture and configuration conventions.

---

## Requirements Source
The complete specification for this work is in `adr/requirements_20261124-103445.md`:
it carries the source schemas and payload samples, the transformations, the API surface, the
acceptance criteria (AC-1..AC-9), the non-functional requirements and the open questions this
plan resolves. The source tables, their columns and the environment-specific connectors are
declared read-only in the shared module `data-catalog`, under
`data-catalog/lending/cards_consumer_credit/` (`consumer_loans.sqrl` for the schemas,
`consumer_loans-test.sqrl` and `consumer_loans-prod.sqrl` for the connectors). The sibling
project `lending` (`lending/lending360.sqrl`, `lending/lending360-shared-package.json`,
`lending/lending360-api/`) is the reference for catalog inclusion, deduplication, API config and
test layout. The catalog's test data lives in `data-catalog/lending/cards_consumer_credit/testdata/`
and is reached through the catalog's own test connectors, so this project does not copy it.

## Data Quality & Observability

- **Build** — The inner join that keeps only payments of personal loans (FR-4) silently drops any
  payment whose `loan_id` does not match a personal-loan record. Auto-loan payments are dropped by
  design, but a genuine personal payment is also lost if the loan feed is missing or late. Add a
  dropped-payment count keyed by source `loan_type` so an operator can tell an expected auto-loan
  drop from a stalled personal-loan feed. The count is exposed as `DQ_Dropped_Payment`; individual
  dropped records are not retained, to keep the result small and the state bounded. This is
  the only blind spot not covered by the catalog's declared NOT NULL and enum guarantees. [FR-4]
- **Skip** — Re-running catalog assertions (NOT NULL keys, amount types, payment-status enum) would
  duplicate the catalog's own guarantees. Per-customer masking and field exclusion are enforced by
  the JWT filter and the API schema, not by data quality checks. Windowed payment-metric
  observations would not be actionable for an unbounded per-loan summary.
- **Reuse** — Treat the catalog's test-time assertions and its documented at-least-once CDC
  guarantee as upstream coverage; deduplication in step 5 is the consumer of that guarantee. The
  catalog `data-catalog/lending/cards_consumer_credit/consumer_loans.sqrl` doc-strings are the
  authority for column meaning and nullability, and the catalog test data is the test fixture.

## Technical Decisions

- **Engine set** is `flink`, `postgres` and `vertx`: Flink processes the streaming dedup and
  aggregate, Postgres backs the served query tables, Vert.x serves the API. The `kafka` engine is
  omitted because there are no mutations or subscriptions; the prod Kafka sources are plain
  connector tables, exactly as the catalog's own package configures them. The pipeline stays
  streaming so a new or changed payment is visible well within the 1-minute freshness target.
- **Catalog reuse** goes through `script.include` with the underscore namespace `data_catalog`
  pointing at the catalog's shared package, mirroring `lending/lending360-shared-package.json`. The
  environment-specific imports resolve to `consumer_loans-test.sqrl` in test and
  `consumer_loans-prod.sqrl` in prod, so the catalog's watermarks (10 s test, 30 s prod) are kept
  and the catalog is never modified (FR-1).
- **CDC deduplication** keeps the latest record per key ordered by the source update timestamp,
  the same deduplication pattern the sibling `lending` project uses, which turns each at-least-once
  stream into one current row per key (FR-2, FR-3).
- **Zero-payment loans in the summary** force the summary to be built from the deduplicated loans
  left-joined to a per-loan payment aggregate, rather than from `LoanPayments` directly; an inner
  join would drop `PL-009` in AC-5. `LoanPayments` itself stays an inner join (FR-4). Counts and
  sums use conditional aggregation so only applied payments contribute (FR-7), and a loan with no
  applied payments yields zeros and a null last-payment date.
- **Authorization** is implemented by mapping the JWT `customer_id` claim into a table-function
  argument, so the claim is never a caller-supplied input, and every query filters on it; the
  loan-id lookups therefore return nothing for another customer's loan (FR-11, AC-6). The base
  query tables are kept out of the direct query interface so no unfiltered endpoint is generated.
  The nested payments on the customer's summary come from a relationship on the summary type.
- **API shape** uses a custom GraphQL schema plus an operations file (as the sibling `lending`
  project) so the three queries are exposed consistently over GraphQL, REST and MCP; result depth
  is set to 2 so the customer query can nest payments under each summary.
- **Auth configuration** uses an inline `oct` key with the HS256 test secret in the test and dev
  overlays, and an issuer/audience/keys block driven by environment variables in prod. The auth
  block is present in every environment's merged config because a script that reads a claim does
  not compile without an auth provider.
- **Tests** are API tests in a test package with inferred-schema disabled, using the catalog's test
  data through the catalog connectors and per-query authorization headers for the two test
  customers and the no-token case.

## Assumptions

- **Freshness**: Assumed results appear within 1 minute of arrival at the source and the pipeline is streaming, per the recommended default. Rationale: the catalog sources carry event time and Flink streaming plus a Postgres sink meets this easily. [impact: high]
- **JWT verification in prod**: Assumed test and dev use an HS256 secret with a fixed test issuer/audience, while prod reads the signing key(s), issuer and audience from environment variables. Rationale: the requirements' recommended default, and the test runner needs a static token. [impact: high]
- **Workload and API load**: Assumed up to 1 million personal loans, 50 million payments, ~100 payment events/s peak and ~50 API requests/s at p99 < 200 ms, per the recommended default. Rationale: sizes the unbounded per-loan aggregate state and the Postgres-backed lookups. [impact: medium]
- **Loans with no payments in the summary**: Assumed every personal loan appears in `LoanPaymentSummary`, with zero counts and sums and a null last-payment date. Rationale: the recommended default and the explicit AC-5 expectation for `PL-009`. [impact: medium]
- **Date of the last payment**: Assumed the latest `applied_date` among applied payments. Rationale: the recommended default and the AC-3 expectation for `PL-115`. [impact: medium]
- **Loan statuses**: Assumed personal loans of every status (`ACTIVE`, `PAID_OFF`, `CHARGED_OFF`, `SETTLED`) are included, unlike the sibling `lending` project's active-only view. Rationale: the requirement filters only on personal-loan type, and AC-3's `PL-115` is not assumed active. [impact: medium]
- **Engine set**: Assumed `flink`, `postgres`, `vertx` without `kafka`, because there are no mutations or subscriptions. Rationale: the minimal-set rule in the configuration guidance; prod Kafka sources do not require the kafka engine. [impact: medium]
- **Catalog include shape**: Assumed the catalog is included under the underscore namespace `data_catalog` via its shared package, with per-environment `environment` values so the test and prod connector scripts resolve. Rationale: the shared-module guidance and the sibling `lending` project. [impact: medium]
- **Other fees**: Assumed `other_fees_cents` is carried in `LoanPayments` but excluded from the summary totals. Rationale: the recommended default; the request lists late fees only. [impact: low]
- **API protocols**: Assumed GraphQL, REST and MCP are all exposed, as in the sibling `lending` project. Rationale: the recommended default and the existing project convention. [impact: low]
- **CDC deduplication test coverage**: Assumed the tests rely on the catalog test data only and therefore no snapshot proves FR-2/FR-3, because that data has no repeated keys. Rationale: the request says to use the catalog's test data and the recommended default accepts this gap. [impact: low]
- **Budget/template**: Assumed the same engine pattern as the sibling `lending` project and no separate UI. Rationale: no budget is stated and a web UI is explicitly out of scope. [impact: low]
