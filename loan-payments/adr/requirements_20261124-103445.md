# Requirements: Loan Payments (personal loans)

## Goal

Give customers of the retail bank a self-service view of the payments on their personal loans. The view shows each payment and a per-loan payment summary. Customers read it through an API. The SSO JWT authorizes each request, and a customer sees only their own loans.

## Scope

**In scope:**

- Read the personal loans and the loan payments from the shared data catalog, consumer lending data (`data-catalog/lending/cards_consumer_credit/consumer_loans`).
- Keep only the payments of personal loans.
- Build the table `LoanPayments` (one row per payment) and the table `LoanPaymentSummary` (one row per loan).
- Expose lookups by loan id and by customer id. A JWT `customer_id` claim restricts every lookup.
- Tests that use the catalog's test data.

**Out of scope:**

- Auto loans, mortgages and credit cards, and their payments.
- Loan applications and delinquency events.
- Writes of any kind: payment submission, payment changes, mutations.
- Staff, admin or cross-customer access (for example a bank agent who reads any customer).
- Changes to the shared data catalog. The catalog is mounted read-only. This project builds on it and does not re-declare its tables.
- A web UI.

## Functional requirements

- **FR-1**: Read the personal loans (`consumer_loans.Personal_Loan`) and the loan payments (`consumer_loans.Loan_Payment`) from the shared data catalog, through the catalog's environment-specific connector files (`consumer_loans-test.sqrl`, `consumer_loans-prod.sqrl`).
- **FR-2**: Deduplicate the personal-loan CDC stream on `loan_id` and keep the latest record by `source_updated_at`.
- **FR-3**: Deduplicate the loan-payment CDC stream on `payment_id` and keep the latest record by `source_updated_at`. A payment status change (for example `PENDING` to `APPLIED` or `RETURNED`) thus replaces the earlier version of that payment.
- **FR-4**: Keep only the payments of personal loans: a payment stays when its `loan_id` matches a personal loan record. A payment with no matching personal loan is dropped.
- **FR-5**: Produce `LoanPayments`, one row per `payment_id`, with all payment statuses. Each row carries the payment fields and two fields from the loan record: `customer_id` (from `primary_borrower_customer_id`) and `loan_purpose`.
- **FR-6**: Produce `LoanPaymentSummary`, one row per personal loan `loan_id`, with: `customer_id`, `loan_purpose`, the number of applied payments, the number of returned payments, the total amount paid, the principal paid, the interest paid, the late fees, and the date of the last payment.
- **FR-7**: In `LoanPaymentSummary`, compute the total amount paid, the principal paid, the interest paid, the late fees and the last payment date from `APPLIED` payments only. `PENDING`, `RETURNED` and `REVERSED` payments do not add to these values.
- **FR-8**: Expose the payment summary of one loan, looked up by `loan_id`.
- **FR-9**: Expose the payments of one loan, looked up by `loan_id`.
- **FR-10**: Expose all loans of a customer with their summaries, looked up by `customer_id`.
- **FR-11**: Require a valid JWT on every API request. Restrict every result to rows whose `customer_id` equals the JWT `customer_id` claim. A lookup of a loan that belongs to another customer returns no data.

## Sources

### `consumer_loans.Personal_Loan`

- **Ownership**: external. The consumer lending source system owns it. The shared data catalog declares it.
- **Transport**: test: filesystem JSONL `testdata/consumer_loans-personal_loan.jsonl`. Prod: Kafka, as `consumer_loans-prod.sqrl` defines.
- **Format**: JSON.
- **Sample payload** (test data):
  ```json
  {"loan_id":"PL-011","application_id":"LAPP-023","primary_borrower_customer_id":"CUST-066","loan_number":"PL-2020-28229","loan_status":"PAID_OFF","loan_purpose":"MAJOR_PURCHASE","original_amount_cents":1740000,"current_balance_cents":0,"interest_rate":0.1566,"rate_type":"FIXED","original_term_months":24,"remaining_term_months":0,"monthly_payment_cents":84913,"funding_date":"2020-09-11","first_payment_date":"2020-10-11","maturity_date":"2022-09-11","next_payment_due_date":null,"paid_off_date":"2022-09-04","origination_fee_cents":34800,"credit_score_at_origination":644,"dti_at_origination":24.62,"autopay_enrolled":true,"disbursement_account_id":"ACCT-140","payment_account_id":"ACCT-140","origination_channel":"BRANCH","source_system":"CONSUMER_LENDING","source_updated_at":"2022-09-04T12:40:57Z","ingested_at":"2022-09-04T12:44:22Z"}
  ```
  Nullable: `next_payment_due_date`, `paid_off_date`. The catalog schema file `consumer_loans.sqrl` documents every column.
- **Volume and rate**: test data has 170 loans. Prod volume is unknown (see Open Questions).
- **Delivery guarantee**: at-least-once CDC (assumed, as for all catalog CDC streams).
- **Duplicates and ordering**: a CDC update repeats `loan_id`. The latest `source_updated_at` wins.
- **Updates**: CDC upserts of loan state.

### `consumer_loans.Loan_Payment`

- **Ownership**: external. The consumer lending source system owns it. The shared data catalog declares it.
- **Transport**: test: filesystem JSONL `testdata/consumer_loans-loan_payment.jsonl`. Prod: Kafka, as `consumer_loans-prod.sqrl` defines.
- **Format**: JSON.
- **Sample payload** (test data):
  ```json
  {"payment_id":"LPMT-002","loan_id":"PL-001","loan_type":"PERSONAL","payment_amount_cents":79425,"principal_cents":66100,"interest_cents":13325,"late_fee_cents":0,"other_fees_cents":0,"payment_type":"REGULAR","payment_status":"APPLIED","due_date":"2023-12-22","received_date":"2023-12-20","applied_date":"2023-12-20","payment_method":"ACH","principal_balance_after_cents":1940000,"days_past_due_at_payment":0,"confirmation_number":"ACH-20231220-001","return_reason_code":null,"source_system":"CONSUMER_LENDING","source_updated_at":"2023-12-20T10:00:00Z","ingested_at":"2023-12-20T10:03:21Z"}
  ```
  Nullable: `return_reason_code` (set only for returned payments).
- **Volume and rate**: test data has 1,942 payments, 1,010 of them for personal loans. Prod volume is unknown (see Open Questions).
- **Delivery guarantee**: at-least-once CDC (assumed).
- **Duplicates and ordering**: a CDC update repeats `payment_id`. The latest `source_updated_at` wins.
- **Updates**: CDC upserts. `payment_status` can change over time: `APPLIED`, `PENDING`, `RETURNED`, `REVERSED`.

## Time semantics

- **Event-time field**: `ingested_at` (`TIMESTAMP_LTZ(3)`, UTC). The catalog connector files declare the watermark on it: 10 seconds in test, 30 seconds in prod. This project keeps the catalog's watermarks.
- **Version order**: `source_updated_at` decides which CDC version of a record is the latest.
- **Lateness**: the summaries are unbounded aggregates, not windows. A late or updated payment updates the summary of its loan whenever it arrives.
- **Processing time acceptable?**: not needed. The sources carry event time.

## Entities and keys

| Entity | Key | Source | Relation |
|---|---|---|---|
| Personal loan | `loan_id` | `consumer_loans.Personal_Loan` | belongs to one customer, `primary_borrower_customer_id` |
| Loan payment | `payment_id` | `consumer_loans.Loan_Payment` | belongs to one loan, `loan_id` |
| Customer | `customer_id` | JWT claim, and `primary_borrower_customer_id` on the loan | has zero or more personal loans |

## Transformations and aggregations

1. **Latest personal loan**: deduplicate `Personal_Loan` on `loan_id`, latest `source_updated_at` wins (FR-2).
2. **Latest payment**: deduplicate `Loan_Payment` on `payment_id`, latest `source_updated_at` wins (FR-3).
3. **`LoanPayments`**: inner join of the latest payments with the latest personal loans on `loan_id` (FR-4, FR-5). Fields: all payment columns of `Loan_Payment` except the audit columns, plus `customer_id` and `loan_purpose`. The money columns stay in cents.
4. **`LoanPaymentSummary`**: one row per personal loan (FR-6, FR-7). It is an unbounded aggregate over `LoanPayments`, grouped by `loan_id`.

   | Column | Definition |
   |---|---|
   | `loan_id` | the loan |
   | `customer_id` | `primary_borrower_customer_id` of the loan |
   | `loan_purpose` | `loan_purpose` of the loan |
   | `applied_payment_count` | count of payments with `payment_status = 'APPLIED'` |
   | `returned_payment_count` | count of payments with `payment_status = 'RETURNED'` |
   | `total_paid_cents` | sum of `payment_amount_cents` of applied payments |
   | `principal_paid_cents` | sum of `principal_cents` of applied payments |
   | `interest_paid_cents` | sum of `interest_cents` of applied payments |
   | `late_fees_cents` | sum of `late_fee_cents` of applied payments |
   | `last_payment_date` | the latest `applied_date` of applied payments |

   A loan with no applied payments shows zero counts and zero sums, and a null `last_payment_date` (see Open Questions).

   The column names above are a suggestion. The planner may align them with the project's naming.

## Results

### `LoanPayments`

- **Kind**: API (query table).
- **Consumers**: the customer, through the bank's customer-facing app.
- **Authorization**: authorized. JWT claim `customer_id`. A row is visible only when its `customer_id` equals the claim.

### `LoanPaymentSummary`

- **Kind**: API (query table).
- **Consumers**: the customer, through the bank's customer-facing app.
- **Authorization**: authorized. JWT claim `customer_id`. A row is visible only when its `customer_id` equals the claim.

## API surface

- **Queries**:
  - **Loan payment summary by loan id** (FR-8): input `loan_id`. Returns zero or one `LoanPaymentSummary` row.
  - **Loan payments by loan id** (FR-9): input `loan_id`. Returns the `LoanPayments` rows of that loan, newest first (by `received_date`, then `payment_id`), paginated with limit and offset.
  - **Customer loans with summaries by customer id** (FR-10): the customer id comes from the JWT `customer_id` claim. Returns all `LoanPaymentSummary` rows of the customer, each with its payments reachable as a nested relation.
- **Mutations**: none.
- **Subscriptions**: none.
- **Protocols**: GraphQL, REST and MCP, as in the sibling project `lending` (see Open Questions).
- **Access**: every query requires a valid JWT. Every query filters on `customer_id = JWT customer_id claim`, the loan-id lookups included.

## Test data and acceptance criteria

- **Test data**: the catalog's test data, `data-catalog/lending/cards_consumer_credit/testdata/consumer_loans-personal_loan.jsonl` and `consumer_loans-loan_payment.jsonl`. It contains 170 personal loans and 1,010 personal-loan payments (1,001 `APPLIED`, 9 `RETURNED`), and 932 auto-loan payments. 35 personal loans have no payments. 23 customers have more than one personal loan. The test data has no `PENDING` or `REVERSED` payments, and no duplicate `payment_id`.
- **Test tokens**: the tests use JWTs signed with a test key, with `customer_id` claims for the customers below.

**Acceptance criteria:**

- **AC-1** *(FR-1, FR-4)*: `LoanPayments` contains 1,010 rows. No row has a `loan_id` of an auto loan (`AL-*`).
- **AC-2** *(FR-5)*: the `LoanPayments` row of payment `LPMT-002` has `loan_id = PL-001`, the `customer_id` and the `loan_purpose` of loan `PL-001`.
- **AC-3** *(FR-6, FR-7, FR-8, FR-11)*: with a token for `CUST-439`, the summary of loan `PL-115` returns `customer_id = CUST-439`, `loan_purpose = MEDICAL`, applied payment count 11, returned payment count 1, total paid 635,360 cents, principal paid 439,761 cents, interest paid 195,599 cents, late fees 0 cents, last payment date `2026-09-04`.
- **AC-4** *(FR-9, FR-11)*: with a token for `CUST-439`, the payments of loan `PL-115` return 12 rows: 11 `APPLIED` and 1 `RETURNED`.
- **AC-5** *(FR-10, FR-11)*: with a token for `CUST-383`, the customer lookup returns two loans: `PL-055` (`MEDICAL`, 12 applied, 0 returned, total paid 319,560 cents, last payment date `2026-08-28`) and `PL-009` (`DEBT_CONSOLIDATION`, no payments: zero counts and sums, null last payment date).
- **AC-6** *(FR-11)*: with a token for `CUST-439`, the summary and the payments of loan `PL-055` (owned by `CUST-383`) return no data.
- **AC-7** *(FR-11)*: a request without a JWT is rejected.
- **AC-8** *(FR-7)*: for one loan with late fees (for example `PL-035`), the summary late fees equal the sum of `late_fee_cents` of the applied payments of that loan only.
- **AC-9** *(FR-2, FR-3)*: covered by the CDC deduplication logic. The catalog test data has no repeated keys, so no snapshot proves it (see Open Questions).

## Non-functional requirements

- **Freshness**: a new or changed payment shows in `LoanPayments` and `LoanPaymentSummary` within 1 minute of arrival at the source (default, see Open Questions).
- **API latency SLA**: p99 < 200 ms per query, at up to 50 requests per second (default, see Open Questions).
- **Workload**: unknown for prod. Default design point: up to 1 million personal loans and 50 million payments, up to 100 payment events per second at peak.
- **Budget**: not stated (see Open Questions).
- **Reliability**: no data loss. Recovery by replay from the Kafka source topics. Availability 99.9 % (default).
- **Retention**: keep all payments of a loan for the life of the loan and after payoff (default, no expiry).
- **PII and sensitive fields**: the catalog tags `primary_borrower_customer_id` as `@pii` and the payment amounts as `@npi @confidential`. Only the authorized customer sees them. Fields the request does not need stay out of the API: the loan record contributes only `customer_id` and `loan_purpose`, so `loan_number`, credit score, DTI and account ids stay out.
- **Compliance**: GLBA, GDPR, CCPA, FCRA (catalog regulatory scope). The JWT claim filter enforces per-customer access.

## Hard constraints

- Use the shared data catalog's consumer lending tables through `script.include`, as the sibling project `lending` does (`lending360-shared-package.json`). The catalog stays read-only.
- Authorization comes from the JWT `customer_id` claim that the SSO issues.
- The tests use the catalog's test data.
- The project lives in the directory `loan-payments` of the `finance-demo` repository.

## Open Questions

- **Freshness.** Recommended default: *results within 1 minute of arrival (streaming)*. Impact if wrong: high (a daily batch is a cheaper design).
- **Workload and API load in prod.** Recommended default: *up to 1 million loans, 50 million payments, 100 payment events/s peak, 50 API requests/s, p99 < 200 ms*. Impact if wrong: medium.
- **JWT verification in prod.** Which signing algorithm and key does the SSO use (for example RS256 with a JWKS URL), and what are the issuer and audience? Recommended default: *test uses an HS256 test secret. Prod reads the key, issuer and audience from environment variables that the deployment sets*. Impact if wrong: high (prod requests fail verification).
- **Loans with no payments in the summary.** Recommended default: *include every personal loan, with zero counts and sums and a null last payment date*. Impact if wrong: medium.
- **"Date of the last payment".** Recommended default: *the latest `applied_date` of applied payments*. The alternative is the latest `received_date` of any payment. Impact if wrong: medium.
- **Loan statuses.** Recommended default: *include personal loans of every status (`ACTIVE`, `PAID_OFF`, `CHARGED_OFF`, `SETTLED`)*. The sibling project `lending` shows only `ACTIVE` loans. Impact if wrong: medium.
- **Other fees.** The request lists late fees, not `other_fees_cents`. Recommended default: *keep `other_fees_cents` in `LoanPayments`, leave it out of the summary*. Impact if wrong: low.
- **API protocols.** Recommended default: *GraphQL, REST and MCP, as in the sibling project `lending`*. Impact if wrong: low.
- **CDC deduplication test.** The catalog test data has no repeated `payment_id` or `loan_id`. Recommended default: *rely on the catalog test data only, as the request says, and accept that no snapshot proves FR-2 and FR-3*. Impact if wrong: low.
- **Budget.** Recommended default: *the same engines as the sibling project `lending` (Flink, Postgres, Kafka, Vert.x)*. Impact if wrong: low.
