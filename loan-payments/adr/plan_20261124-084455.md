# Implementation Plan: Personal Loan Payments API

**Scenario**: pipeline
**Task**: new-project
**Date**: 2026-11-24T08:44:55Z
**Status**: DRAFT

A new DataSQRL pipeline in `loan-payments/` that reads the shared `data-catalog` consumer-loan
sources, builds a per-loan payment summary and a per-payment table, and serves them through a
JWT-authorized GraphQL/REST/MCP API. It reuses the catalog connectors, its test data and the
project layout of the sibling `lending/` project, and adds no data of its own.

---

`data-catalog` module (sibling directory, read-only) supplies the source tables `Personal_Loan`
and `Loan_Payment` and their test data; the project imports them and never copies or edits them.

## Data Quality & Observability
- **Build** — none new. The one credible silent-loss point is the inner join from personal
  payments to `Personal_Loan`: a `PERSONAL` payment whose loan record never arrives would vanish
  from `LoanPayments` and undercount its summary. The catalog already guarantees this cannot
  happen (`LoanPaymentReferencesValidPersonalLoan_Test` in
  `data-catalog/lending/lending-ontology.sqrl`), so no capture table is warranted. FR-8 is handled
  by construction (latest-version dedup feeding an unwindowed re-aggregation), not by monitoring.
- **Skip** — do not repeat the catalog's referential-integrity, enum, or numeric-sanity assertions;
  do not add ingestion counters for the two sources, because the independent-sender failure mode
  does not apply and the catalog's root snapshot queries already surface content changes; do not
  monitor the intentional auto-loan exclusion, which is a required filter, not an anomaly.
- **Reuse** — the catalog's lending-ontology assertions and root-ontology snapshot queries, and the
  `lending/` project's convention of carrying no pipeline-local DQ tables.

## Technical Decisions
- A custom GraphQL schema plus operations (not an inferred schema) is used, because `customer_id`
  must be injected from the JWT rather than accepted from the caller and the exposed type names are
  fixed; the API is configured like `lending/lending360-api/`.
- The engine set is Flink + Postgres + Vert.x. No `kafka` engine is enabled: the API has no mutation
  or subscription, and the catalog's Kafka sources are external Flink connectors that do not need
  the DataSQRL-managed Kafka engine.
- The catalog is included through one of its top-level package files with the batch mode disabled,
  exactly like the sibling `lending/` base config; the consumer's per-environment configuration
  selects which catalog connector file it imports, so the included module's own environment setting
  never reaches the running pipeline.
- CDC streams are reduced to the latest version per key ordered by the source update timestamp, and
  the summary is an unwindowed re-aggregation, so a late or changed payment updates the API within
  the streaming freshness target instead of waiting for a window boundary.
- `LoanPaymentSummary` is anchored on the latest personal loans and left-joins the applied-payment
  aggregates. Grouping only the payments would omit the loans that have none, which the accepted
  Open-Question default requires to appear with zero counts and a null last payment date.
- Authorization is implemented as claim-injected table functions and relationships over an internal
  state table, with a per-environment Vert.x auth provider; a required claim argument produces the
  required authorization error when the claim is absent.

## Assumptions
**FR-8 coverage**: Assumed FR-8 is verified by construction — the latest-version `DISTINCT` feeds an
unwindowed re-aggregation — and documented in the README instead of by a snapshot. Rationale: no
catalog payment changes status, and the scope forbids adding synthetic source data of our own.
[impact: low]

**Catalog include config**: Assumed the catalog is included with one of its top-level package files
and `is_batch` false (as `lending/` does) while the consumer's `environment` selects the connector
file. Rationale: the consumer imports only the `-{{environment}}` connector, so the include's own
environment setting is inert. [impact: medium]

**Freshness**: Assumed new or changed payments appear within one minute through the streaming Flink
pipeline with no window. Rationale: the recommended default in `### Open Questions`, and the
catalog watermarks (10 s test, 30 s prod) are used as-is. [impact: high]

**JWT validation**: Assumed HS256 with a fixed test secret in `test` and a key from `${JWT_SECRET}`
in `prod`, with issuer and audience supplied as environment variables. Rationale: the recommended
default in `### Open Questions`. [impact: high]

**Production workload**: Assumed up to 1,000,000 personal loans, 50,000 payments per day, and a
50 requests/second peak. Rationale: the recommended default; it only affects deployment sizing.
[impact: medium]

**Dev/local environment**: Assumed only `test` and `prod` overlays, because the scope names exactly
those two and follows `lending/`. [impact: low]

**Loans without payments**: Assumed `LoanPaymentSummary` returns a row for every personal loan, with
zero counts/sums and a null `last_payment_date` when no applied payment exists. Rationale: the
recommended default and the acceptance criterion for `PL-011`. [impact: medium]

**Loan status**: Assumed the API exposes loans in every status, not only `ACTIVE`. Rationale: the
recommended default, and the scope keeps all statuses. [impact: medium]

**Last payment date**: Assumed the latest `applied_date` among applied payments. Rationale: the
recommended default in `### Open Questions`. [impact: low]

**Total amount paid**: Assumed `total_paid_cents` is the sum of `payment_amount_cents` of applied
payments. Rationale: the recommended default in `### Open Questions`. [impact: low]

**Customer-query loan details**: Assumed the signed-in customer's loans also show `loan_status`,
`original_amount_cents`, `current_balance_cents`, `monthly_payment_cents` and
`next_payment_due_date`. Rationale: the recommended default in `### Open Questions`. [impact: low]

**API protocols**: Assumed GraphQL, REST and MCP, matching `lending/`. Rationale: the recommended
default and `### API surface`. [impact: low]

**Budget**: Assumed the smallest DataSQRL Cloud deployment size. Rationale: the recommended default;
no budget was given. [impact: low]
